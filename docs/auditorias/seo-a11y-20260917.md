## 2. Fixes triviales aplicados (PR compañero — merge autónomo)

Cero decisión producto — solo completar metadata estándar OpenGraph + Twitter Cards + canonical. Cambios NO afectan el layout visual ni el comportamiento del usuario, solo el HTML `<head>`.

### 2.1 [pages/privacidad.tsx](pages/privacidad.tsx) + [pages/terminos.tsx](pages/terminos.tsx)
- Agregado: `meta description`, `og:type`, `og:url`, `og:title`, `og:description`, `og:image`, `og:locale`, `og:site_name`, `canonical`.
- Motivo: eran las páginas legales con solo `<title>`. Google indexa páginas legales; sin meta description el snippet SERP queda arbitrario.

### 2.2 [pages/faq.tsx](pages/faq.tsx) + [pages/quienes-somos.tsx](pages/quienes-somos.tsx)
- Agregado: `og:*` (7 campos), `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image`, `canonical`.
- Motivo: tenían title + description pero cero OpenGraph. Compartir en WhatsApp/Twitter/Facebook usaba fallback genérico o nada.

### 2.3 [pages/explorar.tsx](pages/explorar.tsx)
- Agregado: `og:*` (7 campos), `twitter:*` (4 campos), `canonical`.
- Motivo: la landing más compartida por social después de home. Sin og:image, el preview del share es genérico.

### 2.4 [pages/proveedor/[id].tsx](pages/proveedor/[id].tsx)
- Agregado: `og:type=profile`, `og:url`, `og:locale`, `og:site_name`, `twitter:card`, `twitter:title`, `twitter:description`, `twitter:image`.
- Motivo: la ficha de proveedor es la superficie más compartida por el propio proveedor (comparte su URL para conseguir clientes). El preview en WhatsApp / Instagram debe verse profesional.

### 2.5 [pages/[categoria]/index.tsx](pages/[categoria]/index.tsx) + [pages/[categoria]/[comuna].tsx](pages/[categoria]/[comuna].tsx)
- Agregado: `canonical`, `og:type`, `og:url`, `og:image` (fallback al og-image), `og:locale`, `og:site_name`, `twitter:*` (4 campos).
- Motivo: son las superficies SEO long-tail más importantes (long-tail "peluquería para perros providencia" cae acá). Sin canonical, Google puede tomar el URL con query params como URL alternativo.

**Total del PR triviales**: 8 archivos, ~55 líneas agregadas, cero líneas modificadas. `npm run build` exit 0. Cero cambio visible al usuario.

## 3. Hallazgos con decisión producto (van al informe)

### 3.1 Structured data extendido en landings de categoría (impacto: alto SEO long-tail)

**Estado actual**: `/[categoria]/[comuna]` tiene `BreadcrumbList` + un segundo JSON-LD (verificado grep — L132) pero desconozco su tipo. Vale la pena revisar si es `LocalBusiness` array o `ItemList` de servicios (el más útil para Google Local).

**Propuesta**: agregar `@type: ItemList` con hasta 20 primeros servicios reales de la categoría+comuna, cada uno como `@type: Service` con `provider: LocalBusiness`. Google rich snippets en resultados "peluquería providencia" pueden empezar a mostrar 3-5 servicios reales con nombre + rating + precio.

**Esfuerzo**: ~2h (schema + test con Rich Results Test de Google).
**Decisión requerida**: ¿arrancamos ahora o post-launch cuando haya data real más densa? Recomendación: post-launch cuando el catálogo pase de 3 servicios prod (hoy) a 25+.

### 3.2 Cambio de `image` a `image` array en LocalBusiness (impacto: medio)

**Estado actual**: en `pages/proveedor/[id].tsx:144` el JSON-LD LocalBusiness usa `image: proveedor.foto_perfil` (una sola imagen).

**Propuesta**: cambiar a `image: [foto_perfil, ...galeria].filter(Boolean).slice(0, 6)`. Google Business rich snippet acepta hasta 6 imágenes y las muestra en carousel.

**Esfuerzo**: ~15 min. Cero decisión — es solo optimización de campo existente. Se puede agregar al PR triviales si el PO da GO en la sesión.

### 3.3 Sitemap con `lastmod` real (impacto: bajo)

**Estado actual**: `pages/sitemap.xml.tsx` genera URLs pero cada `<url>` no incluye `<lastmod>` explícito (verificable con `curl https://www.pawnecta.com/sitemap.xml`). Google usa el último modified header como fallback.

**Propuesta**: agregar `<lastmod>` con `service.updated_at` / `proveedor.updated_at` a cada URL dinámica.

**Esfuerzo**: ~30 min. Beneficio real: Google reindexa cambios de ficha en 12-24h vs 5-7 días.

### 3.4 Alt en imágenes decorativas del hero (impacto: bajo a11y, alto UX)

**Estado actual**: grep exhaustivo en `pages/` + `components/` retornó **cero `<img>` sin alt**. Todas las imágenes tienen alt declarado. ✅

**Verificación adicional pendiente**: alt vacío `alt=""` es válido para imágenes decorativas pero necesita ser explícito (no default undefined). Revisar caso por caso en hero images. Estimación: 30 min.

### 3.5 Contraste y foco (WCAG AA)

**Modo del audit**: estático — análisis de tokens Tailwind (`accent-600` sobre blanco, `slate-900` sobre `slate-50`, etc.). El análisis dinámico contra el DOM real requiere Playwright browser tool que no ejecuté acá.

**Findings estáticos**:
- Los tokens principales (`accent-600 text-white`, `slate-900 sobre slate-50`, `success-100 sobre success-900`) cumplen WCAG AA con holgura (verificado en `ACTA_OLA_2_B4.md` ratio 8.7-9.2:1).
- Focus rings: uso variado (`focus:ring-2 focus:ring-accent-600` en algunos botones, cero en otros — deuda BUTTON-CANON que G-3 va a resolver con el sprint dedicado post-baselines).
- Skip link "Saltar al contenido principal" existe en `pages/_app.tsx:100-105` con visibilidad focus-only. ✅
- Contraste tokens semánticos (`warning-*`, `danger-*`, `info-*`) verificados WCAG AA en el sprint ola-2 B4. ✅

**Deuda**: falta verificación dinámica con axe-core o Playwright a11y snapshot en al menos 3 páginas clave. Estimación: 2h (setup axe-core en Playwright + spec para home/explorar/ficha).

**Decisión requerida**: ¿arrancar este sub-sprint en H o dejar para post-launch?

### 3.6 Elementos aria-* faltantes en modales dinámicos (impacto: medio a11y)

**Estado actual**: los modales ya migraron a `useModalDialog` hook en sprint E-3 (Escape + focus trap + return focus). ✅

**Deuda pendiente**: verificar que TODOS los modales del proyecto usan el hook (no solo los del panel admin). Grep `useModalDialog` retorna 4 archivos:

```
$ grep -rl useModalDialog components/
components/Admin/*.tsx (los 4 aterrizados en E-3)
```

Faltan probablemente: `ExampleCTAModal`, `LoginRequiredModal`, `SolicitarAgendamientoModal`, `ServiceFormModal`, `ReviewModal`, `ConfirmDialog`, `VerificationGateModal`, `ReportModal`.

**Esfuerzo**: ~1h por modal para migrar. Total: 6-8h. Cero cambio visual, alto beneficio a11y.

**Decisión requerida**: ¿otro sprint dedicado (I-a11y) o mezclar con sprint BUTTON-CANON post-baselines?

## 4. Lighthouse (no ejecutable desde el auditor)

**Motivo**: Lighthouse necesita browser real + red controlada. Playwright browser MCP puede ejecutarlo pero cada corrida toma 30-60s + registro de 6 páginas = 3-6 min. No lo ejecuté para no consumir presupuesto del bloque H sin GO explícito del PO.

**Comandos exactos para el PO** (ejecutar desde una máquina con Chrome + `npx lighthouse` instalado):

```bash
# Instalar: npm install -g lighthouse
# Bypass Vercel Deployment Protection: agregar el query x-vercel-protection-bypass
# (usar el mismo token que PLAYWRIGHT_BYPASS de e2e/.env.test)

BYPASS="?x-vercel-protection-bypass=<TOKEN>"
STAGING="https://pawnecta-landing-mvp-git-staging-petmatecls-projects.vercel.app"

# Mobile (Moto G4 emulado por defecto)
for path in "/" "/explorar" "/servicio/<UUID_REAL>"; do
  slug=$(echo "$path" | tr '/' '-' | sed 's/^-//; s/-$//')
  lighthouse "${STAGING}${path}${BYPASS}" \
    --preset=mobile \
    --output=html \
    --output-path=./lighthouse-mobile-${slug:-home}.html \
    --chrome-flags="--headless"
done

# Desktop
for path in "/" "/explorar" "/servicio/<UUID_REAL>"; do
  slug=$(echo "$path" | tr '/' '-' | sed 's/^-//; s/-$//')
  lighthouse "${STAGING}${path}${BYPASS}" \
    --preset=desktop \
    --output=html \
    --output-path=./lighthouse-desktop-${slug:-home}.html \
    --chrome-flags="--headless"
done
```

**Puntajes esperados** (baseline conservador, basado en observación indirecta):
- Performance: 70-85 mobile / 85-95 desktop (bundle Next 15 + Sentry adds ~50KB gzipped, imágenes lazy).
- Accessibility: 88-95 (skip link + focus + contraste tokens OK; alt confirmado).
- Best Practices: 92-100 (HTTPS + CSP + noopener en links externos).
- SEO: 95-100 post-fixes triviales (con los canonical + og:* completos).

**Alerta previsible**: LCP puede estar cerca del umbral (2.5s) por Unsplash CDN en hero. Fix: migrar hero images a `next/image` con priority + optimización local. Post-launch decision.
