## Resumen ejecutivo

**Cero funciones "sin callers" candidatas a REVOKE inmediato**. Los 201 registros se reparten en dos grupos claramente separados:

1. **186 funciones de la extensión `btree_gist`** (~92%): tipos-internas de PostgreSQL. Instaladas por default con `CREATE EXTENSION btree_gist` para permitir índices GiST sobre tipos básicos (int, float, date, time, text, etc.). **NO tocar** — REVOKE rompe los índices GiST de tablas del proyecto (agenda F1/F2 usa GiST sobre `tstzrange`). Todos declarados como `PUBLIC EXECUTE` por el extension owner, comportamiento estándar.
2. **13 funciones del proyecto** (~7%): las que efectivamente el team escribió + las 2 helpers de agenda. Cada una tiene un caller legítimo (verificado por grep en `lib/`, `pages/`, `components/`).

**Veredicto global**: cero acción inmediata requerida. La superficie efectiva es 13 funciones bien acotadas, cada una con caller documentado. El "204" del kickoff no es una superficie de riesgo — el 92% son extensions internas.

## 1. Categorías (agrupado por rol)

### 1.1 Extension `btree_gist` — 186 funciones — DEJAR COMO ESTÁ

Grupos internos del extension:

- **`gbt_<tipo>_*`** (compress, consistent, decompress, distance, fetch, penalty, picksplit, same, union) para 24 tipos base (bit, bool, bpchar, bytea, cash, date, enum, float4, float8, inet, int2, int4, int8, intv, macad, macad8, numeric, oid, text, time, timetz, ts, tstz, uuid, var). **~166 funciones**.
- **`gbtreekey<N>_in/_out`** para claves de índice (2, 4, 8, 16, 32, var). **12 funciones**.
- **`<tipo>_dist`** (cash, date, float4, float8, int2, int4, int8, interval, oid, time, ts, tstz). **13 funciones**.

**Veredicto**: **necesita anon** — parte del extension `btree_gist`. Cero acción.

**Motivo de retención**: el proyecto usa GiST sobre `tstzrange` en la agenda (F1 slots + F2 estadías) para prevenir overlaps eficientemente (`EXCLUDE USING gist (proveedor_id WITH =, slot_range WITH &&)`). Revocar cualquier `gbt_*` rompe los índices GiST asociados. La política de Supabase es dejar los extensions con `PUBLIC EXECUTE` (mismo criterio que en su gestor de RLS).

**SQL de verificación** (opcional): confirmar que el `btree_gist` extension está instalado + que sus funciones son las que aparecen acá:

```sql
SELECT e.extname, count(d.objid) AS num_functions
FROM pg_extension e
LEFT JOIN pg_depend d ON d.refobjid = e.oid AND d.deptype = 'e' AND d.classid = 'pg_proc'::regclass
WHERE e.extname = 'btree_gist'
GROUP BY e.extname;
```

## 2. Candidatas a REVOKE — 5 funciones con veredicto "sin uso real anon"

### Grupo A — dead code o legacy (3 funciones)

**Veredicto**: cero caller confirmado en el código actual. REVOKE anon (y opcionalmente DROP FUNCTION post-verificación).

```sql
-- CANDIDATAS DEAD CODE — verificar con grep + auditor antes de aplicar.
REVOKE EXECUTE ON FUNCTION public.incrementar_vistas_servicio(uuid) FROM anon;
REVOKE EXECUTE ON FUNCTION public.send_notification(uuid, text, text, text, text, jsonb) FROM anon;
REVOKE EXECUTE ON FUNCTION public.try_jsonb(text) FROM anon;
```

**Riesgo**: bajo — cero caller en pages/, components/, lib/. Si alguna RPC interna las usa via `SELECT` dentro de otra función con SECURITY DEFINER, sigue funcionando (los privilegios del creator se preservan bajo SECURITY DEFINER). Solo se pierde el acceso desde cliente anon directo, que no existe hoy.

**Verificación previa PO** (opcional): confirmar con `pg_depend` que las 3 funciones no son referenciadas por otras funciones/vistas del schema.

```sql
SELECT DISTINCT n.nspname || '.' || p.proname AS dependent_function
FROM pg_depend d
JOIN pg_proc p ON p.oid = d.objid
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE d.refobjid IN (
  'public.incrementar_vistas_servicio(uuid)'::regprocedure,
  'public.send_notification(uuid, text, text, text, text, jsonb)'::regprocedure,
  'public.try_jsonb(text)'::regprocedure
)
AND d.deptype = 'n';  -- normal dependency
```

Si retorna filas → REVISAR antes de REVOKE. Si cero filas → REVOKE seguro.

## 4. Anexo — SQL de re-verificación post-REVOKE

Tras aplicar cualquier lote, verificar con:

```sql
-- Confirmar que la función ya NO tiene EXECUTE a anon:
SELECT has_function_privilege('anon', 'public.<function>(<args>)'::regprocedure, 'EXECUTE');
-- Debe retornar `false`.

-- Confirmar que sigue siendo accesible desde service_role:
SELECT has_function_privilege('service_role', 'public.<function>(<args>)'::regprocedure, 'EXECUTE');
-- Debe retornar `true` (los REVOKE de arriba solo remueven a anon, no a service_role).
```

**Rollback**: si un REVOKE rompe algún caller inesperado, restaurar con:

```sql
GRANT EXECUTE ON FUNCTION public.<function>(<args>) TO anon;
```
