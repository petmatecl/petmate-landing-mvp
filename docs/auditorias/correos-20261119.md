## Gates de entorno (`lib/resend.ts`)

El wrapper `safeSend` aplica **gate estricto a producción**:

- `IS_PROD = NEXT_PUBLIC_APP_ENV === 'production' || (NODE_ENV === 'production' && !NEXT_PUBLIC_APP_ENV)`
- En prod → envío real al destinatario.
- En staging / preview / dev → `to` sobrescrito por `AUDIT_INBOX`, subject prefijado `[STAGING] (orig: ...)`.

**Corolario**: cero riesgo de correos de prueba filtrados a usuarios reales desde previews. Gate verificado por inspección del código; para smoke post-deploy: hacer una reserva ficticia en preview → verificar que el correo aparece en `AUDIT_INBOX`, no en el inbox real del tutor.

---

## Crons: gate a prod

Todos los endpoints `pages/api/cron/*.ts` invocan `skipIfNonProd()` de `lib/cronGuard.ts`. En staging/preview retornan `{ skipped: true, env }` sin tocar BD ni enviar correos. El schedule declarado en `vercel.json` corre en cualquier deploy con el archivo pero el handler se auto-silencia. Cero riesgo de doble disparo del cron desde preview.

Precisión de schedule (Pro plan, 2026-08-04): per-minute. Los crons disparan al minuto exacto del cron declarado. `0 22 * * *` = 22:00 UTC en punto.

### Caso borde 2 — Servicio borrado entre reserva y correo

**Escenario**: proveedor borra o pausa (`activo=false`) el servicio justo después de que el tutor hace la reserva, pero antes de que el email salga (ventana de ~1-5 segundos típica entre INSERT y fetch del endpoint).

| Correo | Comportamiento actual | Riesgo |
|---|---|---|
| Nueva reserva → proveedor (5) | Join `.select('...servicios_publicados!agendamientos_servicio_id_fkey...')` con `.maybeSingle()`. Si el servicio fue DROP físico, el join retorna `servicio: null`. El código hace `servicio?.titulo \|\| 'tu servicio'` → email sale con "tu servicio" genérico. | **OK con fricción** — email sale pero genérico. El proveedor puede confundirse si tiene varios servicios. |
| Update reserva → tutor (6) | Idem patrón. Fallback a copy genérico. | **OK con fricción** |
| Reserva confirmada → tutor (7) | Idem. El tutor ve "Tu reserva está confirmada — tu servicio" (sin título específico). | **CONVIENE** — fricción visible a user final. Fix: incluir snapshot del título del servicio en `agendamientos` al INSERT para persistirlo. |
| Recordatorio 24h (11) | Cron filtra por `servicio.id` NOT NULL en L163 (`if (!servicio?.id) continue`). Reservas con servicio borrado **no reciben recordatorio**. | **BLOQUEA (si el flow es común)** — si un proveedor borra el servicio tras reservas pendientes, ambos tutor y proveedor se quedan sin recordatorio 24h. Verificar que el FK `agendamientos_servicio_id_fkey` sea `ON DELETE RESTRICT` (lo correcto) y no `SET NULL` (lo peligroso). |

**Recomendación**:
1. Pre-freeze: verificar FK `agendamientos_servicio_id_fkey` con `SELECT confdeltype FROM pg_constraint WHERE conname = 'agendamientos_servicio_id_fkey'` → debe ser `'r'` (RESTRICT). Si es `'n'` (SET NULL) o `'c'` (CASCADE), hay problema estructural.
2. Post-launch: snapshot del título del servicio en `agendamientos.servicio_titulo_snapshot` al INSERT. Igual que ya se hace con capacidad_snapshot / capacidad_snapshot_estadia.

### Caso borde 3 — Tutor canceló su cuenta antes del correo

**Escenario**: tutor se registra, reserva un servicio, luego borra su cuenta (`DELETE FROM auth.users`) antes de que el proveedor confirme la reserva (ventana de minutos a horas).

| Correo | Comportamiento actual | Riesgo |
|---|---|---|
| Update reserva → tutor (6) | Endpoint `/api/agendamientos/notify-tutor` hace `supabaseAdmin.auth.admin.getUserById(tutor.auth_user_id)`. Si el user fue borrado, `authUser.user` es undefined o error. Catch devuelve `200 { skipped: true, reason: 'no_email' }`. | **OK** — no rompe el flow proveedor, no envía email a inbox inexistente (rebote). |
| Reserva confirmada → tutor (7) | Idem. | **OK** |
| Recordatorio 24h (11) | Cron hace `supabaseAdmin.auth.admin.getUserById(...)` en batch. Si el user fue borrado, `tutorAuth.data?.user?.email` es `''` → email sale a destinatario vacío → Resend rechaza antes de enviar. | **MENOR** — Resend loguea el fallo pero cron sigue con el resto. Verificar que la métrica de bounces no contamina. |

**Pregunta abierta**: ¿qué pasa con la reserva huérfana? Si `tutor_id` apunta a un `usuarios_buscadores.id` cuyo `auth_user_id` fue borrado de `auth.users` pero la fila `usuarios_buscadores` sigue (según policy FK), la reserva sigue viva en BD + el proveedor la ve. Hoy no hay flow "cuenta cancelada" en la plataforma (no existe endpoint `/api/auth/delete-account`). La única forma de borrar cuenta hoy es admin manual. **Impacto para 2026-11-25**: cero. No es flow user-facing.

### Caso borde 6 — Rate-limit emailLimiter se dispara

**Escenario**: tutor envía 100 reservas en rápida sucesión (no hay flow legítimo que lo haga, pero bug o abuso).

| Correo | Comportamiento actual | Riesgo |
|---|---|---|
| Transaccionales 1-10 | `emailLimiter(req, res)` in-memory. Supera umbral → response 429. El fetch client-side falla silente (`.catch(err => console.warn)`). | **MENOR** — user puede reservar más de las expected, pero los emails post-umbral no salen. Confusión potencial pero no bloqueante. |

**Caveat documentado**: rate limit es in-memory. En Vercel serverless cada invocación arranca con memoria fresca → el counter NO persiste entre invocaciones → el limit es casi no-efectivo en prod. Documentado como deuda P1 en `staging-setup/MASTER_AUDIT_REPORT.md #15`. Fix real requiere Upstash Redis (ya hay plan L1-A4 aterrizado para rate limit de login; el de emails es deuda separada).
